# 运维设计说明

## 本次审查发现

原实现存在会直接影响运维结果的问题：备份覆盖 PATH、条件表达式缺少空格且没有创建备份目录；服务控制含语法错误；远程批量检查与文档不符；CPU 仅统计用户态、负载无条件显示正常；采集失败仍返回成功；测试使用 `set -e` 配合自增导致首个测试提前退出；安装覆盖已有命令且忽略测试失败；通知 JSON 未转义且吞掉请求错误；日志清理会删除其他日志。

这些问题需要修正执行契约，而不是增加更多命令。脚本规模较小，因此保留 `bin/` 独立入口与现有调用方式，不引入插件系统、配置执行器或守护进程。公共库只保留可选展示、日志和通知能力；核心脚本不依赖安装位置，软链接调用无需额外路径解析。

## 验证方法

运行 `bash tests/test_toolkit.sh`。测试覆盖语法、非法参数、systemctl 失败传播、备份恢复对比及失败清理、主机清单校验、混合探测结果、日志末行无换行和异常行、健康状态优先级、未配置通知与安装冲突。模拟探测只能验证编排，不能证明真实网络可用。

Linux 上还应运行真实采集：`bash bin/health_check.sh`，与 `/proc/stat`、`/proc/meminfo`、`df -Pk`、`df -Pi` 对照。CPU 包含 user/system/nice/irq/softirq/steal，空闲部分包含 idle/iowait；不重复计算 guest。磁盘和 inode 默认只检查 `/`，对数据盘分别传入 `DISK_PATH`。负载阈值按每核计算，旧配置 `LOAD_THRESHOLD=10` 需要重新评估。

## 生产接入

1. 在目标 Linux 发行版运行测试和真实采集，确认依赖和采集权限。
2. 使用测试目录演练备份恢复。数据库先使用数据库原生备份工具；本工具不提供事务一致性和远端容灾。选择管理员控制的备份目录。
3. 先 `--dry-run` 检查服务操作，再对非生产服务验证权限与失败退出码。
4. 在受控目标验证端口成功、拒绝和超时；TCP 成功后仍需应用健康接口/业务验证。
5. 配置通知后由操作员主动验证接收端，注意 HTTP 成功不等于通用 Webhook 业务成功；不要将 token 提交进仓库。
6. Cron 明确 PATH、环境变量和日志去向，并监控非零退出码。保留策略交由备份系统和 logrotate 管理。

## 后续增强优先级

先按真实需求增加应用层 HTTP 健康检查、备份恢复演练和容器 cgroup 指标；有监控平台接入需求再增加结构化输出。多主机执行、自动修复、凭据管理和定时调度优先由已有 Ansible、监控及调度系统承担，避免在 Shell 中重复建设。
